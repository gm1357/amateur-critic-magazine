# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start Vite dev server
- `npm run build` — type-check (`tsc -b`) then build for production
- `npm run preview` — preview the production build
- `npm run test:unit` — run unit tests with Vitest once (non-watch)
- `npm run test:unit:watch` — run unit tests in watch mode
- `npm run test:browser` — run browser tests headlessly once (Playwright, Chromium + Firefox)
- `npm run test:browser:watch` — run browser tests headlessly in watch mode
- `npm run test:browser:headed` — run browser tests with a visible browser
- `npm run test:all` — run unit tests then browser tests
- `npm run lint` — lint with Oxlint (`.oxlintrc.json`)
- `npm run fmt` — format with Oxfmt (`.oxfmtrc.json`)
- `npm run fmt:check` — check formatting without writing
- `npm run typecheck` — type-check with `tsc -b --noEmit` (the `-b` matters: without it, `tsc` follows no project references and checks zero files)
- `npm run check` — run `fmt:check`, `typecheck`, and `lint` together
- `npm run commit` — commit via Commitizen (conventional-changelog prompt)

Run a single Vitest test by name: `npx vitest run -t "<test name>"` (add `--config=vitest.browser.config.ts` for browser tests).

## Required workflow after code changes

- Always run `npm run check` after making code changes to verify formatting, types, and lint all pass.
- Always add or update unit tests (`tests/unit/*.spec.ts`) or browser tests (`tests/browser/*.spec.tsx`) for any behavior you add or change.
- Always run the relevant test command (`npm run test:unit` and/or `npm run test:browser`) after making changes, and confirm it passes before considering the change done.
- Split work into **vertical slices**: each commit ships data, component, route, style, and tests together as a working increment. Never a commit that is one layer ("all the CSS", "all the components") or that defers its tests to a later commit.

## Architecture

A movie-review aggregator that reads like a print magazine: `/` is the cover, `/contents` is the table of contents, `/introduction` opens the issue, and each subsequent page is one review.

### The magazine

- `src/main.tsx` mounts `<App/>` into `#root` inside `StrictMode`, wrapped in `<BrowserRouter>`. `src/App.tsx` holds the routing. That split is deliberate — it lets browser tests render `<MemoryRouter><App/></MemoryRouter>` and drive the app by URL.
- **react-router v8, declarative mode** (`<Routes>`/`<Route>`, not `createBrowserRouter`) — all data is a compile-time glob, so there are no loaders or pending states. (How much _paper_ that data takes is measured at runtime — see **Typesetting** — but nothing is ever fetched.) Note **`react-router-dom` does not exist in v8**; import everything from `react-router`.
- `src/App.tsx` is **one route** — `<Route path="*" element={<Magazine/>}/>` — because `src/pages.ts` is the issue's URL contract. A route table would restate that mapping in a second place, and it could never render the pages the URL is _not_ pointing at, which is most of what the magazine puts on screen.
- `src/components/Magazine.tsx` is the whole page: the desk, a `<Spread/>`, `<PageNav/>`, and a `window` keydown effect for Left/Right arrow paging. It renders pages by looking the pathname up in `pages`, never from a matched route.
- `src/components/PageContent.tsx` dispatches on `Page.article.kind` (`cover` | `contents` | `introduction` | `review` | `blank` | `back`). It is the only place that turns a model entry into a page component, so any page can be rendered anywhere. An article that flows is handed to `Paginated` whole on every one of its pages; the page only decides which column of it is on the paper.
- The issue is read as an **open book**: `src/spread.ts` models it as a stack of leaves, where leaf `L` carries `pages[2L]` on its front and `pages[2L+1]` on its back. Spread `s` is therefore the back of leaf `s-1` facing the front of leaf `s`, which is why the cover — page one, the front of the first leaf — sits alone on the right. `spreadOf(mode, i)` is `⌈i/2⌉`.
- **Mode** (`single` | `spread`) is part of the model, not a detail beside it: two facing A4 pages need about a laptop's width before either is readable, so below `64rem` (`src/useMode.ts`) the issue opens one leaf at a time and `spreadOf` is the identity. Every model function takes the mode.
- `anchorOf` is the URL a spread is addressed by, and it **must** be a right inverse of `spreadOf` — a page turn that landed on a URL belonging to a different spread would make the magazine immediately turn again to correct itself. `tests/unit/spread-model.spec.ts` asserts that round trip as a property.
- Paging steps by **leaf, not by page**: two facing pages are one turn, so on a wide desk Next moves past both. Reading one leaf at a time this is the same step it has always been, which is why the pager prints a range (`2–3 / 6`) only when there is a range to print.
- **Turning a page.** `planTurn(from, to, direction)` in `src/spread.ts` arranges four slots — two static halves plus the front and back of the leaf in the air — so that at 0° the composition is pixel-identical to the spread being left and at ±180° pixel-identical to the one being joined. Every edge case falls out of that property rather than being special-cased: the cover opening onto bare desk, the book closing, the blank recto at the back, one leaf at a time, and a contents entry several spreads ahead rendering as a single believable turn.
- The URL is the only thing that turns a page. `src/useFlip.ts` watches the spread under the pathname and animates the difference, so the pager, the arrow keys and every link animate through one path. Its effect deps are primitives and state objects only — a dep on anything _derived_ (a spread, a plan) is a fresh object every render once the compiler is not memoising, which is the case in the browser tests, and the magazine would turn pages forever.
- The turn runs on the **Web Animations API**, not a CSS transition: `finished` is a reliable promise, it still resolves at `duration: 0` (which is how reduced motion lands the leaf instantly rather than stranding the state machine), `cancel()` interrupts it, and a keyframe effect cleanly overrides the inline angle a drag writes. `fill: 'forwards'` is not optional — without it the last frame is dropped before React commits the landed spread and the leaf snaps back for a frame.
- `.leaf-turn` must never carry `overflow`, `opacity`, `filter` or `contain: paint`. Any grouping property forces `transform-style: preserve-3d` to compute to `flat` and the turn collapses into a 2D squash. Clipping belongs on `.leaf-face`. `tests/browser/flip.spec.tsx` asserts the computed transform is a `matrix3d` for exactly this reason.
- Perspective and the 3D context exist **only while a leaf is in the air** (`[data-phase]` on the book), and the page scrollers are frozen for the same window. At rest the paper carries no transform at all, so type rasterises crisply and no browser is asked to composite a scrolling page inside a 3D context — which is the Firefox trouble spot this avoids by construction rather than by workaround.
- **Dragging.** `src/useFlip.ts` binds `pointermove`/`pointerup`/`pointercancel` on `window` once and reads the live gesture out of a ref, so a drag never re-renders the four pages under it: the angle is written straight to the node as `--flip-angle`. That is not only a performance choice — the compiler is off in the browser tests, so a state-per-move design would behave differently in the environment the assertions run in. `setPointerCapture` is attempted in a `try`/`catch`: a real pointer gets the niceties, a synthetic one has nothing to capture and the window listeners cover it either way.
- The URL moves when the reader lets go, not when the paper lands. That keeps `target === turning.to` the _only_ guard against a drag turning the page twice; deferring the navigation would need a suppression flag and would make a Back press mid-turn ambiguous.
- That navigation lands **one commit after** the state that starts the settle, because it comes from a `window` listener rather than a React handler. So the location effect runs once with the leaf already flying towards its new spread and the URL still on the old one — a reading indistinguishable, from the state alone, from the reader asking for a different page mid-turn. `seenTarget` in `src/useFlip.ts` is what tells them apart: the mid-air re-target fires only when the URL has actually _moved_, never when the turn's own state churns. Without it a released drag snapped the leaf flat and turned it again from nothing, which is what `tests/browser/drag.spec.tsx` now watches the whole angle track for — a forward turn may never go backwards.
- **Swiping.** A finger may take the page anywhere, not only by its edge: a non-mouse `pointerdown` on the book opens a _provisional_ gesture with no direction, and the first movement past `swipeThreshold` decides — across the page turns it, down the page is left to the browser. The start is rebased at that moment so the leaf begins at the fingertip rather than jumping a threshold's worth to meet it. A mouse is not offered this: the page edge is the more precise instrument and the less accidental one.
- `touch-action: pan-y` belongs on **`.leaf-page` as well as `.a4-leaf`**: a touch resolves its touch-action from the element it landed on up to _that element's scroll container_, so a scroller between the two would keep the leaf's declaration from ever reaching a finger inside the page. Left to `auto`, Chrome claims any touch that travels past its slop — in either direction — and sends `pointercancel`, which means every swipe on a real phone landed back where it started while the synthetic pointers in the browser suite (never cancelled, so never affected) all passed. The edge grips are `none`. Anything that adds a scroller inside a page has to carry `pan-y` with it.
- Most of the contents page is links, so refusing to swipe from them would leave it nearly unswipeable. A swipe therefore wins over the entry it began on, and the click it would otherwise fire is swallowed by a capture-phase listener — cleared a tick after release, so it never eats the reader's next real click. A tap is a swipe that went nowhere, and still follows the link.
- All the drag arithmetic is pure and in `src/flip.ts` (`dragProgress`, `settleTarget`, `remainingTravel`, `turnDuration`, `trail`, `flickVelocity`), so it is tested in node rather than through a browser. The component holds no arithmetic.
- A flick is measured over a **window** (`VELOCITY_WINDOW`, via a bounded `trail` of samples in the gesture ref), never from the last pair of frames. A finger slows as it lifts, so a page genuinely thrown across reads as stationary at the moment it is released; and a single fast frame under a stuttering browser reads as a throw when nothing was thrown. That second failure is what used to make `tests/browser/drag.spec.tsx` flake in Firefox about one run in three.
- The **bookmark** is a labelled tab in the book rather than on a page, for the same reason the pager is: printed on the paper it would turn away with it. `Spread` hangs it from the very foot of the left-hand leaf — which, reading one leaf at a time, is the only leaf there is — centred on that leaf and clear of it, so none of it is printed over the page's own copy. `isPastContents` in `src/pages.ts` decides whether it is printed at all, comparing by leaf so a listing continued over two of them is still the listing. It is a `Link`, so pulling it turns the page through the same path the pager and the arrow keys take. It is a **pure scale of the leaf** like the type on the page, `--bookmark-drop` being the whole of its reach below the paper — tab plus the travel of the hover pull. Which is why `magazine-chrome` gives that much up as `padding-top`: the tab hangs into the band the pager shares, and the band is a fixed `--desk-chrome` tall, so the pager centres in what is left rather than the band growing to fit. That reservation is the whole reason a leaf-relative tab fits at all — grown against `--leaf-w` with a centred pager it would land on the folio on a wide desk — so `tests/browser/bookmark.spec.tsx` checks the hit area clears every control in the band at four viewport sizes, and that the tab holds its proportion to the page across them. Reaching for it **grows** the tab rather than moving it: its top edge is pinned to the paper's edge and only the end below travels, so it reads as the bookmark being drawn further out of the book instead of a card coming loose from the page. The label is stacked `Go to` / `contents` by a newline in its own text under `white-space: pre-line` — not a `<br>`, which some engines drop from the accessible name without a space — and set solid at `line-height: 1`, since capitals have no descenders to clear and the fixed band has no room to spare. It is held against the _end_ of the tab rather than its top, so the words ride down with it and the new length opens above them — which is the way round a bookmark actually leaves a book: what is printed on it travels with the end, and the blank part appearing is the part that was still between the pages. That is a transition on `height`, which means it also animates when the desk changes size and the leaf takes the tab with it — harmless on screen, but it is why the proportion test polls for a settled height rather than measuring once. The `Link` takes its size from the tab, so the hit area grows with it. The black rule round its three open edges is a `::before` rather than a `border`, so it can sit a small margin inside the card the way a border is printed inside the trim; anchored to the bottom, it travels with the end like the label does. Its colour, `--bookmark-edge`, is the one palette entry that does **not** change for print — the cut edge of a piece of card is black on screen and on paper alike, the way `--color-curl` is. Browsers floor a border to whole device pixels, so its thickness is picked to still come out at two of them on the smallest leaf the issue is ever set at.
- The running head and folio are printed on each leaf; the pager is not. A control printed on a page would turn away with it, so `PageNav` stands on the desk under the book, sized to the book's width and following the URL rather than the paper.
- Every page is one **A4 leaf** (210 × 297 mm, ISO 216) on a `bg-desk` backdrop. The desk owns the ruler: `magazine-desk` in `src/index.css` derives `--leaf-w` from physical A4 capped by whichever viewport axis runs out first (minus `--desk-chrome`, the height the pager takes), and the book, the leaves and the pager are all measured off that one value. The leaf's height comes from `aspect-ratio`, never from the content. That only holds because the page sits in a `min-h-0 flex-1 overflow-hidden` wrapper and an article longer than the leaf is **continued on the next one** rather than stretching it or scrolling inside it.
- **The leaf** is the `@container`, and a page is a **pure scale of itself**: every length on it is `cqw`, `em`, `%` or `ch`, so the ratio of type to paper is the same on a phone as on a wall. Nothing inside a page may be sized in `vw`/`vh`, `px` or `rem` — the ruler is one page, not the viewport and not the open book. (Put the container on the spread instead and every page would set its type twice as large the moment the desk got wide.) Body copy is `--page-type` on the desk — one knob, in `cqw` — and everything smaller or larger on a page is an `em` of it. The scale was drawn against a base of `2cqw`, so `1rem ≡ 2cqw` is the conversion to use when moving a fixed length onto a page. The hairline borders are the one exception left: a rule is 1px at every size, the way it is on paper.
- Because the page is a pure scale, **how long the issue is does not depend on the screen** — 28 pages from a 320px phone to a 3400px desk. That is a property of the type being leaf-relative, not something the model enforces, which is why the composing room still measures rather than assuming.
- `@page { size: A4 portrait }` plus a `print:` pass on the layout means Ctrl-P prints the real thing: the desk and pager drop away, each leaf takes its true 210 × 297 mm, and a spread's blank half is not a page at all. The break is `.a4-leaf ~ .a4-leaf { break-before: page }` — _between_ leaves rather than after them, so the last page does not push a blank sheet out of the printer. A `@media print` palette override at the end of the palette block keeps the paper white, since the screen palette is dark.
- Pagination is **not** derived from `useParams`. `src/pages.ts` builds an ordered `Page[]` and `findPageIndex(pages, pathname)` matches on the pathname. A `-1` index means "not a page of this issue" — the single signal that renders the 404 and hides the running head and pager.
- The contents is an article of the issue like any other, so it paginates, continues and prints for free. It reads its folios back out of the typeset `pages` via `findPageNumber`, so an article that grew a page renumbers the listing with it rather than leaving it to drift.

### Typesetting

- **Nothing scrolls.** A printed page cannot grow a scrollbar, so an article too long for its leaf is continued on the next one. That is the whole reason the model below exists.
- The split is **article vs page**. An `Article` is a piece of content the issue knows at compile time (the cover, the contents, the introduction, one review); a `Page` is one leaf, and carries the article on it plus `part`/`parts`. How many pages an article takes is _not_ a property of the content — it is a fact about type on a page, and no amount of reading the JSON will say how many lines it sets to.
- So `pages` is **state, not a constant**. `src/pages.ts` exports `articles` (compile time) and `buildPages(articles, parts)` (the expansion); `src/useTypeset.ts` holds the measured counts and rebuilds the model; `src/issue.ts` carries the result down as context, which `Leaf` and `Contents` read for their folios. The module-level `pages` export is the _untypeset_ issue — one leaf per article — and is only the context's default and a convenience for tests that do not care.
- **The composing room** (`src/components/ComposingRoom.tsx`) is where the counting happens: every flowing article is laid out once, off the desk, inside a real `Leaf` — the same components in the same frame, so what is counted is what will be printed — and reports how many columns it fragmented into. It is `position: fixed`, `height: 0`, `visibility: hidden` and `aria-hidden`, and it **unmounts as soon as the issue is `settled`**, so a magazine at rest is not carrying a second copy of every article in the DOM or the accessibility tree.
- The fragmenting is **CSS multi-column**, not measurement: `.page-flow` is one column wide with `column-fill: auto`, so the browser breaks the article into leaf-sized columns exactly as it would break it for a printer, and `transform: translateX(...)` brings the wanted column onto the paper. Nothing in the app measures a line or counts a word — `Paginated` only divides `scrollWidth` by the column width to learn how many there were.
- The clip is on `.page-window` and the margins are on `.page-box`, because **overflow is clipped at the padding edge**: one box holding both showed a margin's worth of the neighbouring column down either side of every page.
- Article roots must be **block flow, not flex**. Browsers do not reliably fragment a flex container across columns, so `Contents`, `Introduction` and `ReviewPage` stack with margins; small flex rows inside them are fine, and carry `break-inside-avoid` so an entry is never split in half.
- A continued page is addressed by `partPath`: the first page keeps the article's own URL (`/reviews/clue`), and the rest count up from two (`/reviews/clue/2`). `nearestPage` catches a reader standing on a page that re-typesetting has taken away, and Magazine only acts on it once `settled`, because before the issue is counted _every_ continued URL looks like a page that does not exist.
- Re-cutting the issue is **not a page turn**. `useFlip` takes an `edition` — mode plus the typeset counts — and when it changes it moves the leaf instead of flying it. Without that, the first paint's renumbering animated a turn from wherever the provisional model had put the reader.
- That correction happens **during the render**, not in an effect. An effect runs after the browser has painted, so there would be one committed frame holding a spread counted against the old cut and read against the new one — a different page entirely. On screen nobody sees it, because the corrected frame lands immediately after; a printer does. `page.pdf()` lays the document out at paper width, which flips the mode and re-cuts the issue to a single leaf, and it photographs exactly that frame: printing any review used to hand back a different review. `tests/browser/spread.spec.tsx` watches every state the desk passes through during a re-cut, because a bug nobody can see on screen needs a test that does not blink.
- Two facing pages of one article are two windows onto the same copy of it, so `Spread` marks the recto `silent` and `Paginated` puts `aria-hidden` on it. Otherwise a continued listing is read out twice. The other side of that trade: a screen reader on page two of an article hears the whole article, because every page holds the whole flow.
- An unknown slug is just a pathname `pages` does not list, so it takes the same `-1` path as any other address outside the issue. `ReviewPage` takes its `slug` as a prop and never touches the router.

### Looking closer

- Zoom is a **view laid over a fixed page**, never a change to it. `.magazine-zoom` carries a `scale()` inside `.magazine-viewport`, which is exactly the size the book is at fit. A transform does not change what a leaf _measures_, so `cqw`, the column count, the folios and `edition` are all untouched: **zooming must never re-typeset the issue**. If a folio ever moves because somebody looked closer, the transform has leaked into layout — `tests/browser/zoom.spec.tsx` watches for exactly that.
- **Nothing is on at rest**, the same rule perspective follows. At fit there is no transform, no clip and no `touch-action` override — all three are gated on `[data-zoom='in']`. That is what keeps type rasterising crisply, and it is what lets a turning leaf overhang the paper: under perspective a leaf in the air projects well outside the book's box, and a window clipped to the book would **slice it**. The clip has to be conditional for that reason alone.
- Panning is the browser scrolling the viewport, which is where the **clamping** comes from — free and exact, because a scroll offset cannot leave its own content. The pan is still driven from pointer deltas written straight to `scrollLeft`/`scrollTop` rather than left to the browser, because `touch-action: none` is what stops a drag being claimed as a scroll and the pointer cancelled underneath it. A drag therefore never re-renders the pages under it, the same discipline `useFlip` keeps.
- `touch-action` is `pan-y` at fit — a horizontal swipe turns the page — and `none` while zoomed. It must be declared on **`.page-window` as well as `.a4-leaf` and `.leaf-page`**: the window clips the columns, which makes it a scroll container, and a touch resolves its touch-action only as far as _its own_ scroll container. Without it the leaf's declaration never reaches the type, so a drag that began on a word behaved differently from one that began on a margin — the browser was free to claim it. The magnified page is `user-select: none` for the other half of the same problem: a finger coming down on the type would otherwise start choosing words rather than moving the paper. Starting a pinch _from_ fit needs more than the attribute: touch-action is **latched when a touch sequence begins**, so one flipped as the second finger lands is already too late for the pinch that flipped it. A non-passive `touchstart` that preventDefaults multi-touch only is the escape hatch; a single finger is never touched, so a tap still follows its link.
- The wheel listener must be **native and non-passive**. React attaches `wheel` passively, so `preventDefault` from an `onWheel` prop is silently ignored and the browser zooms the whole document instead of the page. A trackpad pinch arrives here as a wheel with ctrl held.
- `useFlip.abort()` is the one seam between the two gesture systems: the moment a press becomes a pinch or a pan, whatever the flip had opened is let go of exactly the way a `pointercancel` lets it go. Otherwise a pinch's first finger drifts past `swipeThreshold` and turns the page out from under the gesture.
- A double tap is derived from the **pointer stream** (`isDoubleTap`), not from `dblclick`: engines synthesise that from a finger differently and some not at all. It is offered to a finger only — a mouse has the buttons and the wheel, which are more precise instruments and less accidental ones, the same reason `useFlip` does not offer a mouse the swipe. A tap on a link is the reader following it, so it neither zooms nor arms the next tap.
- All the arithmetic is pure and in `src/zoom.ts` — `anchoredScroll` is what keeps the point under the fingers where it is — and is tested in node, the same split `src/flip.ts` keeps.
- The pager and the zoom controls share `.magazine-chrome`, which owns `--desk-chrome`. Anything added to that band must **not** grow it: that height comes straight off every leaf in the issue. The bookmark hanging into its top strip is the standing example — the band gives up `--bookmark-drop` as `padding-top` and the pager centres in the rest, rather than the band getting taller.

### Review data

- Reviews are JSON files in `src/data/reviews/<slug>.json` with `movie`, `score`, `date` (ISO `YYYY-MM-DD`), `review`, and an optional `hearted`. **The filename is the slug.**
- `hearted` is a boolean, and the one optional field: it comes from a marker that is present or absent, so an absent field means "not hearted" rather than a malformed review. `parseReview` normalises it to `false`.
- `score` is a **whole number from 1 to 10**, rendered by `ScoreBadge` as five stars at one point per half star. The half star is a clip, not a glyph: two identical star rows are stacked and the filled one is clipped to `score * 10`% of the width, so the cut always lands on a glyph edge or its exact midpoint. The badge carries `role="img"` with an `aria-label` of `"<score> out of 10"` — that label is what tests locate it by.
- `src/data/reviews.ts` picks them up with `import.meta.glob({ eager: true })` and sorts by `date` ascending, tie-broken by slug (glob key order is not stable across platforms).
- `src/data/review.ts` hand-rolls validation and throws naming the offending file and field. Date checking is two-step — an ISO shape test plus a `Date` round-trip — because `new Date('2026-02-31')` silently rolls over rather than failing.
- Because the glob is eager, the parser runs at **module evaluation**, so a malformed JSON does not fail `vite build` — it blanks the page at runtime. `tests/unit/reviews-data.spec.ts` imports the real `reviews` array specifically to turn that into a failing test run.
- A review may have a **film still** in `src/data/frames/<slug>.{avif,jpg,jpeg,png,webp}` — the filename is the slug, as with the JSON. `src/data/frames.ts` globs them eagerly as URLs, and `indexFrames` throws for a frame that matches no review or a review with two, so a typo in a filename fails `tests/unit/frames.spec.ts` rather than silently never printing. A review without one keeps its plain paper.
- The still is printed full bleed from the top of the paper, over the running head, down to the masthead's rule. It is drawn by **`Leaf`**, not the article, because the article is read through `.page-window`, which clips to the text box. How far down it runs depends on how the title wraps, so `ReviewFrame` **measures** it: the masthead (`[data-masthead]`) is found inside the frame's own leaf, so a spread, a turning leaf and the composing room never read each other's, and its foot is summed from `offsetTop`s rather than client rects, because offsets are layout and a leaf magnified by the zoom or tilted in a turn measures what it would lying flat. The depth is written straight to the node as `--frame-depth`, in `cqw` of the leaf — the same pure scale as the type — so a leaf laid out at another size (a wider desk, the printer) takes the still with it before anything has measured again, and a `ResizeObserver` on the masthead and the leaf re-measures after. It was anchor-positioned once (`bottom: anchor(--masthead bottom)`); that is not used because it is still missing from too many engines, and the still vanished on them. The leaf is `relative isolate` for it: the box it is positioned in and measured from, and the stacking context that puts `z-index: -1` above the paper and under the type. Type over it takes the `on-frame` palette, which is light at both ends of the theme the way `--bookmark-edge` is black at both.

### Toolchain

- **Tailwind v4** via `@tailwindcss/vite`, wired into **both** `vite.config.ts` and `vitest.browser.config.ts`. There is no `tailwind.config.js` and no PostCSS — configuration is CSS, in `src/index.css`.
  - The issue is **dark only** — there is no light theme and nothing reads `prefers-color-scheme`; `:root` declares `color-scheme: dark`. The palette lives in plain `:root` custom properties with a `@media print` override (white paper for the printer), surfaced through **`@theme inline`**. The `inline` is load-bearing: without it Tailwind inlines the value at build time and the print override never reaches the utilities. JSX takes no `dark:` prefixes.
  - The drop cap is a `@utility drop-cap`, applied as `first:drop-cap`.
  - Oxfmt does not sort Tailwind classes, and Tailwind only sees class-name _literals_ — never build one by string concatenation.
- **React Compiler** is enabled via `@rolldown/plugin-babel` + `reactCompilerPreset()` in `vite.config.ts`. This auto-memoizes at build time, so manual `useMemo`/`useCallback`/`React.memo` are unnecessary — write plain React. Note the compiler is _not_ wired into `vitest.browser.config.ts`, so browser tests run uncompiled.
- TypeScript uses solution-style config: `tsconfig.json` references `tsconfig.app.json` (app source, `strict`, bundler resolution) and `tsconfig.node.json` (build tooling). `tests/` is in neither, so **test files are not type-checked**.
- Two Vitest configs, split by directory:
  - `vite.config.ts`'s `test.dir` → `tests/unit/`, node environment, no DOM. Parser and page-model tests live here.
  - `vitest.browser.config.ts` → `tests/browser/`, real Chromium + Firefox via `@vitest/browser-playwright`. Its `browser.viewport` is **pinned** (414 × 896) rather than inherited, because it decides whether the suite reads the issue as a spread or one leaf at a time. `tests/browser/spread.spec.tsx` is the one file that widens it, and hands the size back in an `afterEach`.
  - **Firefox never runs two files in one browser.** With several pages open in one Firefox, Playwright delivers input to the wrong one — a click from one file landed mid-drag in another, and the click that file asked for never arrived — so every gesture test failed at random, about one per run. The pages already have separate content processes, so the leak is in the shared browser process: the config deals the specs across three Firefox instances (`firefox-1`…`firefox-3`, each its own browser, each `fileParallelism: false`), read off the directory so a new spec is never left out. Chromium stays one parallel instance. Do not merge the Firefox instances back into one parallel one to simplify the config.
  - Because the issue typesets itself, **a test cannot import how long it is**: page numbers and which pages face each other depend on the desk they were laid out on. `tests/browser/issue.ts` (not a `*.spec.*`, so it is not collected) reads the magazine's own account instead — `folioOf`, `totalOf`, `openAt` — and turns are asserted as moves from wherever the issue happened to open.
  - Browser tests use `vitest-browser-react`'s `render` (awaited) with locator assertions (`await expect.element(...).toBeVisible()`), not `@testing-library/react`. `userEvent` comes from `vitest/browser`. Flat `test()` calls, no `describe`, relative imports — there are no path aliases.
  - `userEvent` has **no low-level pointer API** — the Playwright provider offers `click`, `hover`, `dragAndDrop` and friends, none of which can hold a button down and report an exact position on the way across. `tests/browser/pointer.ts` (not a `*.spec.*`, so it is not collected) dispatches real `PointerEvent`s instead: constructible in both browsers, no hit-testing, and able to stop at an exact progress. Dispatch on the **element**, never on `window` — an event dispatched at the window never travels down to the page, so a broken implementation would still pass. `userEvent.dragAndDrop` is used once, for real input, and needs `{ force: true, steps: n }`: without `force` the leaf under the cursor fails the drop target's hit test, and the default single move is a drag with no travel to measure.
- Linting/formatting are handled by the Oxc toolchain (Oxlint + Oxfmt), not ESLint/Prettier. VS Code is configured to format-on-save with the Oxc extension (`.vscode/settings.json`).
- Commits are enforced as Conventional Commits via commitlint + Husky's `commit-msg` hook; use `npm run commit` to get the guided prompt.
